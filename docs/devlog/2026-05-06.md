## 1. 오늘 한 작업
- 공용 PC로 프로젝트 개발 환경을 옮기는 작업을 진행했다.
- MariaDB 데이터를 mysqldump로 백업하고 공용 PC에서 복원하는 흐름을 확인했다.
- Elasticsearch snapshot 백업과 복원 과정을 진행했다.
- es_backup repository 등록, snapshot restore, Kibana에서 인덱스 확인 작업을 수행했다.
- 공용 PC에서 Elasticsearch와 Kibana를 실행하고 팀원들이 접속할 수 있는 IP 설정을 점검했다.
- 개인 PC에서 작업하던 ES/Kibana를 공용 PC 기준으로 옮기는 흐름을 정리했다.

---

## 2. 어려웠던 점
- Elasticsearch에서 repository_missing_exception이 발생하며 es_backup repository를 찾지 못하는 문제가 있었다.
- snapshot 파일을 단순히 옮기면 복원될 줄 알았는데, repository 등록과 restore 과정이 따로 필요했다.
- GET _cat/indices?v로 확인했을 때 일부 인덱스 상태나 shard 상태가 예상과 다르게 보여 당황했다.
- localhost로 접속하면 내 PC 기준이 되기 때문에, 팀원들이 접속하려면 공용 PC의 IP를 기준으로 설정해야 했다.
- 192.168.x.x, 100.x.x.x처럼 여러 IP가 보여 어떤 주소를 써야 하는지 헷갈렸다.
- Elasticsearch와 Kibana 설정을 어디까지 바꿔야 하는지도 처음에는 명확하지 않았다.

---

## 3. 해결한 방법
- Elasticsearch에 snapshot repository를 다시 등록한 뒤 restore를 진행했다.
- snapshot 복원 후 Kibana에서 GET _cat/indices?v로 인덱스가 정상적으로 복원되었는지 확인했다.
- 공용 PC 기준의 IP를 확인하고, 팀원들이 접속해야 하는 주소를 정리했다.
- Elasticsearch와 Kibana 설정에서 외부 접속이 가능하도록 host 설정을 점검했다.
- 공용 PC에서 ES와 Kibana가 정상적으로 실행되는 것을 확인한 뒤 개인 PC의 ES/Kibana는 종료해도 되는 흐름으로 정리했다.
- MariaDB는 백업 파일을 기준으로 복원하고, ES는 snapshot restore 방식으로 복원하는 차이를 구분했다.

---

## 4. 느낀 점
- MariaDB 이전과 Elasticsearch 이전은 방식이 완전히 달랐다.
- ES는 파일을 복사하는 것이 아니라 snapshot repository 등록과 restore 절차를 통해 복원해야 했다.
- 공용 개발 환경에서는 데이터 복원뿐만 아니라 IP, 포트, 네트워크 접속 설정까지 함께 맞춰야 했다.
- localhost는 항상 현재 실행 중인 PC를 의미하므로 팀원 접속용 주소로 사용하면 안 된다는 걸 확실히 알게 됐다.
