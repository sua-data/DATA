## 1. 오늘 한 작업
- DATA 프로젝트에서 데이터가 어떻게 흘러가야 하는지 전체 구조를 다시 정리했다.
- 뉴스가 수집된 뒤 원문 저장, 전처리, 키워드 추출, 감성 분석, 관점 분석, 화면 제공까지 어떤 흐름으로 이어지는지 단계별로 나눠봤다.
- MariaDB와 Elasticsearch를 각각 어디에 써야 할지 기준을 잡았다.
- 처음에는 DB에 다 넣으면 되지 않을까 싶었지만, 뉴스 검색이나 키워드 집계까지 생각하면 ES가 필요한 부분이 명확해졌다.
- article_id를 기준으로 DB와 ES를 연결하는 방향을 잡았다.

---

## 2. 어려웠던 점
- DB와 ES를 같이 쓰는 구조가 머리로는 이해되는데, 막상 어떤 데이터를 어디에 넣어야 할지 기준을 잡는 게 어려웠다.
- 기사 본문, 키워드, 감성, 관점은 ES에 두는 게 맞아 보였고, 사용자 정보나 좋아요/싫어요 같은 데이터는 DB에 두는 게 맞아 보였는데, 둘을 어떻게 연결할지가 고민이었다.
- 데이터를 나누면 구조가 깔끔해지는 대신, 나중에 API에서 같이 조회해야 하는 복잡함이 생길 수 있었다.

---

## 3. 해결한 방법
- MariaDB는 사용자, 약관, 로그인 기록, 기사 조회 기록, 좋아요/싫어요, 배치 로그처럼 관계가 중요한 데이터를 저장하는 쪽으로 정리했다.
- Elasticsearch는 뉴스 본문, 키워드, 감성, 관점, 요약처럼 검색과 집계가 필요한 데이터를 저장하는 쪽으로 정리했다.
- 두 저장소를 연결하기 위해 article_id를 공통 키로 사용하기로 했다.
- 이후 기사 상세 페이지나 마이페이지에서도 article_id를 기준으로 데이터를 연결할 수 있도록 생각했다.

---

## 4. 느낀 점
- 저장소를 나누는 건 단순히 DB냐 ES냐의 문제가 아니라, 데이터가 실제 화면에서 어떻게 쓰이는지까지 봐야 하는 문제였다.
- 처음에는 구조가 복잡해 보였지만, 역할을 나눠보니 오히려 각 데이터가 어디에 있어야 하는지 조금씩 명확해졌다.
