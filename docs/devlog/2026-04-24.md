## 1. 오늘 한 작업
- 기사 관련 DB 테이블 구조를 정리했다.
- article_meta 테이블을 기준으로 ES의 기사 데이터와 DB의 사용자 기능 데이터를 연결하는 구조를 잡았다.
- article_views 테이블로 사용자가 어떤 기사를 봤는지 저장하는 방식을 정리했다.
- article_reactions 테이블로 좋아요/싫어요 반응을 저장하는 구조를 설계했다.
- article_id를 DB와 ES에서 공통으로 사용하는 식별자로 확정했다.

---

## 2. 어려웠던 점
- 기사 본문과 분석 결과를 DB에도 넣고 ES에도 넣으면 중복이 너무 커질 것 같았다.
- 그렇다고 DB에 article_id만 두면 나중에 기사 상세 페이지에서 데이터가 부족해 보일 수 있었다.
- article_id 타입도 고민이 됐다. 네이버, 연합뉴스, 한국경제처럼 출처마다 ID 형식이 다를 수 있어서 숫자로만 잡으면 안 될 것 같았다.
- 좋아요/싫어요, 조회 기록은 사용자와 연결되기 때문에 ES보다 DB가 맞는 것 같은데, 기사 내용은 ES에 있어서 둘을 같이 조회해야 했다.

---

## 3. 해결한 방법
- article_id는 문자열 기반으로 관리해 다양한 출처의 기사 ID를 담을 수 있도록 했다.
- DB에는 article_meta, article_views, article_reactions처럼 사용자 기능과 직접 연결되는 데이터만 저장하기로 했다.
- 기사 제목, 본문, 키워드, 감성, 관점, 요약은 Elasticsearch의 news_economy 인덱스에서 관리하도록 분리했다.
- 기사 상세 페이지에서는 article_id를 기준으로 ES의 기사 정보와 DB의 사용자 반응 데이터를 함께 조회하는 흐름으로 정리했다.

---

## 4. 느낀 점
- DB와 ES를 같이 쓰려면 article_id 같은 공통 식별자가 정말 중요했다.
- 모든 데이터를 한 곳에 넣는 것보다, 데이터의 역할에 따라 나누는 게 더 안정적이라는 걸 느꼈다.
- 나중에 프론트 페이지 이동까지 생각하면 ID 설계를 대충 하면 안 된다는 걸 알게 됐다.
