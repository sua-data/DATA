## 1. 오늘 한 작업
- 코드성 마스터 테이블 구조를 정리했다.
- system_codes, error_codes, admin_action_codes, activity_event_types 테이블의 역할을 구분했다.
- 크롤링, 분석, 분류, 키워드 추출 등 처리 단계 코드를 system_codes로 관리하는 구조를 설계했다.
- 실제 FK를 연결하는 과정에서 컬럼 타입과 문자셋/콜레이션 문제를 점검했다.
- 여러 번 테이블을 삭제하고 다시 만들면서 최종 구조를 맞췄다.

---

## 2. 어려웠던 점
- system_codes와 다른 로그 테이블을 FK로 연결하는 과정에서 오류가 발생했다.
- 참조하는 컬럼과 참조되는 컬럼의 타입, 길이, 문자셋, 콜레이션이 맞지 않으면 FK가 걸리지 않았다.
- 이미 만들어둔 system_codes, terms_metadata 같은 기준 테이블은 다른 테이블에서 참조할 예정이라 함부로 삭제하기 애매했다.
- SQL 작성 중 CONSTRAINT 위치나 쉼표 처리 문제로 문법 오류가 발생하기도 했다.
- 테이블 구조를 바꿀 때마다 어떤 테이블을 먼저 지우고 다시 만들어야 하는지 계속 확인해야 했다.

---

## 3. 해결한 방법
- SHOW CREATE TABLE로 실제 테이블 구조를 확인했다.
- FK를 걸기 전에 참조 대상 컬럼과 참조하는 컬럼의 타입, 길이, 문자셋, 콜레이션을 맞췄다.
- system_codes, terms_metadata처럼 기준이 되는 테이블은 최대한 유지하고, 필요한 경우 ALTER TABLE로 문자셋과 구조를 맞췄다.
- 참조 테이블은 기준 테이블이 먼저 생성된 뒤 만들도록 순서를 정리했다.
- SQL 문법 오류가 날 때는 CONSTRAINT 앞 쉼표, FOREIGN KEY 위치, 컬럼 정의 순서를 다시 확인했다.

---

## 4. 느낀 점
- FK 오류는 단순히 “안 된다”가 아니라 타입, 문자셋, 생성 순서, 참조 관계 중 하나가 안 맞아서 발생하는 경우가 많았다.
- DB 설계는 ERD처럼 구조를 그리는 것에서 끝나는 게 아니라 실제로 생성하면서 검증하는 과정까지 포함된다.
- 테이블을 지웠다가 다시 만드는 과정이 반복되면서 오히려 DB 구조를 더 정확히 이해하게 됐다.
