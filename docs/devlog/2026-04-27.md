## 1. 오늘 한 작업
- 배치 작업 이력을 저장하기 위한 테이블 구조를 설계했다.
- batch_jobs 테이블로 배치 실행 단위를 관리하는 구조를 정리했다.
- article_process_logs 테이블로 기사별 처리 성공/실패 이력을 저장하도록 설계했다.
- article_error_logs 테이블로 실패한 기사에 대한 에러 코드와 메시지를 저장하는 구조를 정리했다.
- 실제 테이블 생성 과정에서 FK 연결과 삭제 순서를 확인했다.

---

## 2. 어려웠던 점
- 배치 작업은 전체 실행 단위와 기사별 처리 단위가 달라서 로그를 어떻게 나눠야 할지 고민됐다.
- 처음에는 로그 테이블을 단순하게 만들려고 했는데, 관리자 페이지에서 처리 현황을 보여주려면 더 세분화해야 했다.
- article_process_logs와 article_error_logs를 연결할 때 어떤 값을 FK로 잡아야 할지 헷갈렸다.
- FK가 걸린 테이블은 삭제할 때 순서를 잘못 잡으면 바로 삭제되지 않았다.
- 테이블을 수정하려고 하면 기존 FK 때문에 DROP TABLE이나 ALTER TABLE이 막히는 경우도 있었다.

---

## 3. 해결한 방법
- batch_jobs는 전체 작업 단위, article_process_logs는 기사별 처리 단위, article_error_logs는 실패 상세 기록으로 역할을 분리했다.
- job_id를 기준으로 배치 실행과 기사 처리 로그를 연결했다.
- 실패 상세 로그는 article_process_logs의 history_id를 참조하도록 설계했다.
- 테이블을 다시 만들 때는 FK 의존 관계를 고려해서 하위 테이블부터 삭제하고, 기준 테이블을 먼저 생성한 뒤 참조 테이블을 생성했다.
- SHOW CREATE TABLE로 실제 생성된 테이블 구조를 확인하면서 CREATE TABLE 문을 수정했다.

---

## 4. 느낀 점
- 로그 테이블은 단순히 기록만 남기는 테이블이 아니라, 나중에 관리자 화면과 장애 대응에 쓰이는 데이터였다.
- FK가 있는 테이블은 생성 순서와 삭제 순서가 중요했다.
- 테이블을 여러 번 삭제하고 다시 만든 과정이 힘들긴 했지만, 그 과정에서 참조 관계를 더 잘 이해하게 됐다.
