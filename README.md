# DATA

경제 뉴스 기반 키워드·감성·관점 분석 서비스

> **Team Project | 2026.04 - 2026.05**  
> 담당 역할: 서비스 기획, 요구사항 정의, MariaDB 테이블 설계, Elasticsearch 인덱스 설계

---

## 1. 프로젝트 소개

DATA는 경제 뉴스 데이터를 수집하고 분석하여 일별 주요 키워드, 감성 분포, 관점 흐름과 관련 뉴스 요약을 제공하는 경제 뉴스 분석 서비스입니다.

단순히 뉴스 목록을 보여주는 것이 아니라, 여러 경제 뉴스에서 반복적으로 나타나는 키워드와 이슈를 분석하고 관련 기사를 묶어 사용자가 주요 경제 흐름을 빠르게 파악할 수 있도록 구성했습니다.

본 프로젝트는 팀 프로젝트로 진행했으며, 저는 서비스 기획과 요구사항 정의, MariaDB 테이블 구조 및 Elasticsearch 인덱스 설계를 담당했습니다.

---

## 2. 기획 배경

경제 뉴스는 매일 많은 양이 생성되며, 동일한 이슈도 언론사와 기사마다 서로 다른 제목과 관점으로 전달됩니다.

사용자가 개별 기사를 모두 읽지 않고도 당일 주요 경제 이슈와 전반적인 흐름을 파악하려면 뉴스 데이터를 이슈 단위로 구조화하고 분석할 필요가 있습니다.

DATA는 다음 문제를 해결하기 위해 기획했습니다.

- 많은 경제 뉴스 중 핵심 이슈를 파악하기 어려운 문제
- 동일 이슈와 관련된 기사가 여러 언론사에 분산되는 문제
- 기사별 감성과 관점 차이를 한눈에 비교하기 어려운 문제
- 뉴스 원문과 분석 결과를 체계적으로 저장하고 검색해야 하는 문제
- 수집부터 분석, 저장, 조회까지 이어지는 데이터 흐름이 필요한 문제

## 7. 주요 설계 내용

### 7.1 MariaDB와 Elasticsearch 역할 분리

MariaDB는 사용자, 뉴스 원문, 분석 결과와 통계 데이터를 정형 구조로 관리하는 용도로 사용했습니다.

Elasticsearch는 뉴스 제목과 본문 검색, 키워드 기반 조회와 분석 결과 검색을 빠르게 처리하기 위한 용도로 구성했습니다.

```text
MariaDB
- 뉴스 원문 및 메타데이터
- 분석 결과
- 키워드 통계
- 감성 및 관점 데이터
- 사용자 및 서비스 관리 데이터

Elasticsearch
- 뉴스 제목 및 본문 검색
- 키워드 기반 검색
- 감성 및 관점 조건 검색
- 분석 결과 통합 조회
```

### 7.2 뉴스와 분석 결과 구조

뉴스 원문과 분석 결과를 분리하여 저장하되 기사 ID를 기준으로 연결하도록 설계했습니다.

이를 통해 뉴스 원문은 유지하면서 키워드, 감성, 요약과 관점 분석 결과를 독립적으로 갱신할 수 있도록 구성했습니다.

### 7.3 일별 키워드 통계

일별 주요 키워드와 기사 수, 감성 분포와 분석 지표를 별도 구조로 관리했습니다.

## 13. 개발 중 해결한 문제

### 13.1 뉴스 원문과 분석 결과의 저장 구조

초기에는 뉴스 원문과 모든 분석 결과를 하나의 테이블에 저장하는 방식을 검토했습니다.

하지만 키워드, 감성, 요약과 관점 분석은 처리 시점과 갱신 주기가 다르기 때문에 하나의 구조에 저장하면 확장과 관리가 어려울 수 있었습니다.

뉴스 원문과 분석 결과를 분리하고 기사 ID를 기준으로 연결하여 각 분석 결과를 독립적으로 관리할 수 있도록 설계했습니다.

### 13.2 MariaDB와 Elasticsearch의 역할 중복

뉴스 데이터가 MariaDB와 Elasticsearch에 모두 저장되면서 어떤 데이터를 어느 시스템에서 조회해야 하는지 기준이 필요했습니다.

정형 데이터와 관계 관리, 통계 데이터는 MariaDB에 저장하고 뉴스 전문 검색과 복합 필터 조회는 Elasticsearch에서 처리하도록 역할을 구분했습니다.

### 13.3 화면별 데이터 요구사항 차이

메인 화면, 뉴스 상세 화면, 키워드 분석과 검색 화면에서 필요한 데이터 항목이 서로 달랐습니다.

화면별 요구 데이터를 먼저 정리하고 뉴스 원문, 분석 결과와 집계 데이터가 어떤 API를 통해 전달되어야 하는지 조회 흐름을 구체화했습니다.

### 13.4 뉴스 데이터 중복 가능성

여러 수집 경로에서 동일하거나 유사한 뉴스가 반복 수집될 가능성이 있었습니다.

기사 URL, 제목, 작성 시각과 유사도 분석 결과를 활용하여 중복 여부를 확인하고, 동일 이슈의 기사는 유사 뉴스 그룹으로 묶을 수 있도록 구조를 정리했습니다.

### 13.5 분석 결과 검색 구조

기사 원문뿐 아니라 키워드, 감성, 관점과 요약 결과도 검색 및 필터 조건으로 활용해야 했습니다.

Elasticsearch 인덱스에 원문과 주요 분석 결과를 함께 포함하고, 검색 목적에 따라 필드 타입과 조회 조건을 구분하도록 설계했습니다.

---

## 14. 프로젝트를 통해 배운 점

### 요구사항 정의의 중요성

개발 전에 사용자 기능, 화면별 데이터와 분석 결과의 저장 기준을 정리해야 팀원 간 구현 기준을 맞출 수 있다는 점을 배웠습니다.

### 데이터 구조 설계 경험

뉴스 원문, 키워드, 감성, 요약과 관점 분석 결과를 관계형 데이터베이스와 검색 엔진에 목적에 맞게 분리하여 설계하는 경험을 했습니다.

### 데이터 흐름 이해

뉴스 수집부터 전처리, 분석, 저장, API와 화면 조회까지 데이터가 이동하는 전체 흐름을 이해했습니다.

### 검색 시스템 설계

MariaDB와 Elasticsearch의 차이를 이해하고, 데이터의 특성과 조회 목적에 따라 저장소의 역할을 구분하는 방법을 경험했습니다.

### 팀 프로젝트 협업

각 팀원이 수집, 분석, Backend와 Frontend 기능을 나누어 구현하는 과정에서 요구사항과 데이터 규격을 명확하게 공유하는 것이 중요하다는 점을 배웠습니다.
